# S09 verification — 2026-09-29

Verdict: the normal completion path is fixed, but S09 is not closed across resume boundaries. Three independent safety assertions fail. No production code changed during this audit.

Commit under review: `7c76d4e` (S09). Evidence directory: `evals/results/s09-audit-2026-09-29/`.

## R01 — P1: resume ignores an already-recorded stop decision

Location: `backend/app/iteration.py:102–105`.

With `on_item_error: stop`, the first item's failed result is committed through the real worker's `loop_item` event. Interrupting immediately after that commit leaves no whole-loop checkpoint. On resume, the completed-index branch counts the failure, then unconditionally continues. It never reapplies the stop policy.

Observed: **3 body executions instead of 1**. Later items execute despite the configured stop. This is a control-flow defect, not just a missing warning. A loop body may perform consequential actions; the reproduction uses a controlled Python-tool transport and sends no real external writes.

Probe: `test_resume_preserves_stop_after_failed_item`. Honor a saved failed result under stop before visiting another index, and rebuild the same stopped summary. The underlying replay branch predates S09; S09's new completeness guarantee remains incomplete until this case is covered.

## R02 — P2: restored results bypass size enforcement and lose truncation

Locations: `backend/app/iteration.py:99–105`, `150–155`.

Item progress persists its full value before the accumulated-results size check. Payload shedding changes only the local `results` list, while `dropped` is also local. After an interruption following the final item's durable progress event but before the loop checkpoint, resume restores all full values. Every restored entry takes the early `continue`, bypassing `within_budget`; `dropped` remains false.

Observed: the resumed loop succeeds with `values_dropped: false` and fails the required truncation assertion. The probe lowers the byte limit to 150 for a small deterministic fixture; the same control flow applies to the production limit. This also means the output-size limit is bypassed on this resume path.

Probe: `test_resume_reapplies_result_bound_to_restored_items`. Apply common aggregation/size enforcement to fresh and restored entries. Persist any metadata needed to retain historical payload-loss information; do not allow replay to resurrect oversized values silently.

## R03 — P2: a legacy incomplete checkpoint becomes a complete run

Location: `backend/app/worker.py:144–146`.

The compatibility test verifies that a checkpoint without `summary` resumes, but does not verify its completeness flag. The worker treats absent metadata as `{}` and reports no truncation.

The reproduction uses the same legacy-checkpoint simulation as the existing test: a loop accepted 2 of 3 items, checkpointed, and was interrupted downstream; its `summary` is removed to represent the old format. Resume succeeds but reports **`truncated: false`**.

Probe: `test_legacy_limited_checkpoint_is_not_reported_complete`. Reconstruct what is provable from retained inputs/results/configuration (the max-items omission is provable here), or surface unknown historical completeness explicitly. Missing metadata is not evidence of full completion.
