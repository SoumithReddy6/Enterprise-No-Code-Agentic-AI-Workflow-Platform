## A53-I01 [P1]: recheck pending spend after the awaited save

Location: `backend/app/accounting_state.py:130–139`, used by `registry.call_model` before provider dispatch. The newly enabled concurrency makes the existing single-generation assumption reachable.

`ensure_accounting_ready` observes pending spend, captures its generation and snapshot, awaits a strict save, acknowledges the captured generation and returns. While that save is in flight, another branch can report new usage. The new worker correctly keeps that newer generation pending. The save barrier then returns anyway, allowing a new provider request despite `durability.pending` still being true.

This is different from policy A's allowed overrun by already outstanding calls. This finding concerns a further repair request issued after newer usage is already known but not durable. It does not require a strict token ceiling or a ledger.

### Real Worker reproduction

`probe_pending_spend.py` uses an accepted two-branch workflow:

```text
Input → Fork → extraction Agent A ─┐
             → language model B ──┴→ Join → Response
```

Agent A needs a structured-output repair. The external model endpoint is synthetic; the Worker, Store, policy, structured repair and accounting code are real. Barriers control persistence order rather than depending on a small timeout:

1. A's first response reports 5 tokens. Its best-effort fast save fails, a supported TA02 scenario.
2. Before A's repair, the strict barrier starts saving generation 1 / 5 tokens. Hold that Store call.
3. B returns another 5 tokens: generation 2 / 10 known tokens. Its save waits behind the serializer.
4. Release A's generation-1 save; keep B's newer save unconfirmed.
5. The current code dispatches A's repair. At that exact provider boundary, generation is **2**, acknowledgement is **1**, `pending` is **true**, and stored spend is **5**.

The run later completes successfully with 15 tokens. That final total is correct; it does not establish that the no-further-call-with-unsaved-spend barrier held at step 5. During a storage outage, this permits additional spend before the newer usage is durably acknowledged. No crash-loss quantity beyond the demonstrated unsaved generation is claimed.

### Control and smallest correction

The test-only control repeats the existing save/check operation until `durability.pending` is false. With exactly the same provider responses and persistence schedule, A's repair waits: generation and acknowledgement are both **2**, and stored spend is **10** when dispatch occurs. The final total remains 15 and no action is charged by the barrier.

Recheck the predicate after every awaited save. If another generation arrived, save again before returning to the provider. Keep the current failure behavior (`AccountingUnavailable`), exact committed-generation acknowledgements, and propagation of cancellation/lease loss. Do not clear pending state by acknowledging a generation that was not committed.

This follows the standard predicate-wait pattern: a completed wait does not by itself prove the shared condition now holds; evaluate the condition again. Python documents this behavior in `Condition.wait_for`. Relay need not introduce a Condition or another lock; its existing durability predicate and persistence callback are sufficient. [Python asyncio synchronization documentation](https://docs.python.org/3.12/library/asyncio-sync.html#asyncio.Condition.wait_for).

### Regression needed before closure

Carry this real Agent-repair interleaving into A02 or a focused regression. Assert the durability state and stored total at provider dispatch, not only the final sum. Also cover a refused/failed follow-up save: it must stop the repair with `AccountingUnavailable` and no extra provider call. Existing cancellation and lost-lease behavior must remain intact.

The reproduction and the rechecking control each produced the same result in three successful runs. The control changes only the test process; the repository application remains unchanged. The first exploratory probe used a successor flow node, but LangGraph's super-step barrier kept it from overlapping the unfinished siblings. The final reproduction therefore uses a real in-node Agent repair, which is an allowed branch behavior. [LangGraph execution model](https://docs.langchain.com/oss/python/langgraph/graph-api#graphs).

## Design conformance and deviations

- The publication clock covers action-only snapshots, while spend acknowledgement remains tied to the frozen committed generation. Snapshot selection occurs under the per-attempt mutex. The shielded commit task owns that mutex until its thread finishes.
- Event bodies and invocation-scoped usage remain separate from coalesced accounting. The existing TA03 commit-receipt behavior is retained.
- Branch validation checks closed chains, same-fork joins, width, writes and memory-role Agents through attachment dependencies. Other attachment-shape restrictions are supplied by `split_graph`; control nodes are already invalid attachments.
- Backend and editor use the Join union, and the shared fixture checks that parity. Join remains hidden in the palette.
- D01 as two process-harness rows is acceptable: the harness actually kills a separate worker and resumes from durable data. It is stronger than a simulated cancellation and preserves the intended oracle.
- Removing C's individual cancellation from A04 is acceptable for the stale-snapshot oracle; A03 separately tests cancellation. A04 inspects the commit after the holder, so a later correct commit cannot hide the stale one.
- Relaxing the held save's exact counter is correct because it freezes the newest publication when it acquires the lock. The next-save and final-counter assertions still address the intended ordering defect.
- Product messages without the roadmap name and the added direct-fork-to-Join error are appropriate. The shared binding test extension retains its prior assertions.

These changes do not require another design round. Correct the pending-spend barrier, strengthen its regression, then run the affected accounting/control-flow gates and hosted checks on the correction commit.
