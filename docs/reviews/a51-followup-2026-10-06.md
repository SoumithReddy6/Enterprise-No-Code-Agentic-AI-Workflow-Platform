## F01 — P1: the schema validates a different number from the one returned

`backend/app/agent_runtime.py:66` parses the answer exactly, but line 71 parses it
again with ordinary `json.loads` for schema validation. Line 74 returns the exact
version. A rounded surrogate passes the schema while the returned object violates it.

| Exact input | Schema constraint | Current result |
| --- | --- | --- |
| `1000.00000000000001` | `maximum: 1000` | accepted |
| `1000.00000000000001` | `type: integer` | accepted |
| `0.99999999999999999999` | `minimum: 1` | accepted |
| `1000.00000000000001` | `multipleOf: 0.01` | accepted |
| `1000.00000000000001` | `const: 1000` or `enum: [1000]` | accepted |

The decision to retain float-based schema validation is documented. These probes
quantify its consequence: the declared output contract is not enforced on the output
actually checkpointed and consumed. This concerns bounds, integer types and equality,
not just familiar floating-point difficulties with `multipleOf`.

**Durable-worker reproduction:** an extraction node declaring `maximum: 1000`
checkpoints `{"amount": 1000.00000000000001}` and finishes successfully.

**Separate-process reproduction:** a deterministic local Ollama HTTP fixture returns
that value to the real worker. Its schema accepts the answer, a downstream condition
selects `gt 1000`, and a write node sends one POST to the local receiver. The run
succeeds. A valid output check should repair the answer once, then fail if it still
violates the schema; the downstream write must never execute.

The test write uses a harmless constant JSON body and explicitly disables approval
inside the throwaway workflow. This isolates schema enforcement from the separate
exact-or-refuse rule for request-body numbers. No real recipient or external account
was contacted, and this is not a live-model quality claim.

Fix: validate the same exact numeric object that is returned. Numeric schema keywords
and integer detection need a consistent exact representation, including decimal
operands in the schema. Keep Boolean handling distinct from numbers. Test rejection
and bounded repair for these cases through extraction, checkpointing and downstream
write suppression.

[deployed results](../../evals/results/a51-followup-2026-10-06/deployed-results.json),
and [old/new returned values](../../evals/results/a51-followup-2026-10-06/schema-before-after.json).

## F02 — P2: numeric range errors bypass pre-send refusal handling

`backend/app/exact_json.py:22` passes JSON numeric tokens directly to `Decimal`.
The valid JSON token `1e99999999999999999999` exceeds Decimal's exponent range and
raises `decimal.InvalidOperation`, not `ValueError`. `worker.prepare_write` catches
only `ValueError`, so the exception misses `WriteNotSent`. The attached-agent handler
then converts it to `UncertainWriteError`.

Both a durable-worker probe and a separate-process HTTP reproduction show:

- status `failed`, with "External write outcome is uncertain; reconciliation is required";
- zero receiver requests and no write marker;
- the agent never gets its ordinary tool-error observation, so it cannot correct the
  invalid numeric body and continue.

The same input also produces an unhandled `InvalidOperation` from the condition's
field parser instead of a named numeric-input error. Structured-output parsing misses
its bounded-repair path for the same reason.

Fix: translate unsupported JSON numeric ranges into a specific validation error at
the common parser boundary. HTTP preparation must explicitly refuse that error rather
than use its existing non-JSON-as-text fallback. It should then become `WriteNotSent`
before any marker or network action. Add ordinary-refusal/agent-correction tests and
keep approval, cancellation and lease-loss exceptions escaping unchanged.

Evidence: the `out_of_range_exponent_pre_send` and
`range_refusal_should_be_correctable` rows in the results above.
