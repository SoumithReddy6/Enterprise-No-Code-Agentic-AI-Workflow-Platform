## R01 — P1: JSON numeric fields are rounded before exact comparison

`backend/app/conditions.py:97` uses ordinary `json.loads`; non-integer JSON numbers
become binary floats. `as_number` then creates a Decimal from the already-rounded
float. Decimal comparison cannot recover the discarded digits.

| JSON field | Comparison | Expected | Actual |
| --- | --- | --- | --- |
| `1000.00000000000001` | `gt 1000` | true | false |
| `9007199254740993.0` | `gt 9007199254740992` | true | false |
| `0.100000000000000005` | numeric `eq 0.1` | false | true |
| `1e309` | `gt 1e308` | true, for a Decimal-supported value | rejected as a non-finite float |

The identical first value passed as direct numeric text compares correctly, isolating
the loss to JSON handling. The compiled graph takes the wrong branch too.

**Confirmed with real deployed processes.** A throwaway authenticated API, separate
worker and local HTTP receiver ran two workflows. The `gt` workflow skipped its required
write. The `eq` workflow sent one POST when it should send none. Both runs reported
success. No real workspace, external account or production recipient was used.

**There is an earlier boundary too.** `agent_runtime.validate_structured` at lines
64–70 parses and serializes the extraction answer using floats. An actual compiled
extraction-agent → condition workflow, with a deterministic mocked provider response,
received `{"amount":1000.00000000000001}`, checkpointed `{"amount": 1000.0}`, and
took the false branch. This is a runtime-path test, not a live-model-quality claim.

Fix the numeric contract across both boundaries: preserve numeric precision during
structured-output validation/serialization and field parsing. A change to only the
condition parser is insufficient for the extraction use case. Preserve the existing
text-comparison rules and reject non-finite numeric constants explicitly. Add boundary
cases for ordering, equality and membership through direct JSON input, extraction
output, checkpoint restoration and the HTTP-receiver scenario. Decimal strings are
a verified direct-input control; they avoid this loss while numeric-token handling
remains unfixed.

Evidence: [numeric probes](../../evals/results/a51-audit-2026-10-06/conditions-results.json)
and [deployed receiver results](../../evals/results/a51-audit-2026-10-06/deployed-results.json).

## R02 — P2: invalid Options JSON submits the previous predicate

`ConfigField` in `frontend/components/platform-settings.tsx:77–94` updates its local
draft on every edit but calls `onChange` only after successful JSON parsing. An invalid
edit leaves the last valid `options` in the workflow. Its error is local component state;
`workflow-editor.tsx:491–505` validates `current.current` without consulting that error.
`startRun` uses the same validation path.

**Browser reproduction:** select `in`, enter `["high"]`, then edit it to the invalid
`["urgent",`. An inline JSON error remains, but clicking Validate sends `options:
["high"]` and the editor displays "Workflow is valid and ready to run." The UI and
submitted predicate disagree. A valid connected graph can therefore execute an old
predicate while its visible field contains a failed edit.

This is a pre-existing generic JSON-widget pattern newly exposed by the A5.1 Options
field, not a backend validation bypass. The actual inspector was tested with intercepted
API fixtures: the evidence proves stale configuration submission, not a real remote
write from that browser fixture.

Propagate invalid draft state to the editor and refuse validation/execution until it
is corrected; do not silently submit the earlier list. Preserve the deliberate ability
to save invalid drafts without silently discarding the visible edit. Extend the browser
test from valid operator switches to valid → invalid Options edits, failed execution
submission and subsequent correction.

Evidence: [inspector results](../../evals/results/a51-audit-2026-10-06/inspector-results.json)
and [screenshot](../../evals/results/a51-audit-2026-10-06/invalid-options.png).

| backend | failed |

[Hosted run 37491194394](https://github.com/SoumithReddy6/Enterprise-No-Code-Agentic-AI-Workflow-Platform/actions/runs/37491194394)
reports `1 failed, 985 passed, 2 skipped`. The sole failure is
`backend/tests/test_sandbox.py::test_a_missing_cli_is_reported`: the committed test
adds `/usr/bin:/bin` to PATH, where Ubuntu has a real Docker. It reports `image_missing`
instead of the asserted `cli_missing`. This is an environment-isolation defect, not
evidence that production incorrectly identifies Docker state.

During this review another process changed that test to an empty-only PATH. The auditor
did not make or overwrite the change. With it present, the sandbox file passes 21 tests
and a complete local backend run passes 988. Commit and rerun hosted CI; do not waive
the failed job or claim the milestone's hosted gate is already green. The new browser
and PostgreSQL jobs are now observed passing, so the dated milestone closure note can
be updated accordingly after the backend is resolved.
