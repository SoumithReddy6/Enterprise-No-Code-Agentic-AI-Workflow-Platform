# A5.2: multi-way routing

**Status:** Approved on 2026-10-21 with three review fixes (trusted-input rule, contract 2
only, wording). Plan: [multi-way routing](../plans/2026-10-21-multi-way-routing.md).
**Baseline:** `5cdcd645131ef0e077f862f76c560fda4d192b49`.
**Hosted verification:** all five jobs passed in Actions run `39174617614`.

**Review scope cut:** A5.2 adds no routing-review kind, approval API shape, review UI or
database migration. Switch accepts checked or trusted inputs; unsupported inputs are
refused. A future routing-review feature needs a demonstrated workflow and its own design.

## Outcome and scope

Let a workflow choose exactly one of several named paths using deterministic rules.
For example, a checked support category routes to Billing, Technical, Account or Other.
This is the next roadmap capability after A5.1. It does not expand the request-reader
work, change its admission gate, or certify the reader's recorded 9/20 result as accepted.

Parallel fan-out, waiting for several branches, subgraphs, regex matching and another
model-based router are outside A5.2. A5.3 will address parallel execution separately.

## Approach

Add a new **Switch** node. Reuse the typed Condition predicate implementation for each
case, including exact numbers, field paths and named comparison errors.

Alternatives considered:

- Extend Condition to return arbitrary routes: this changes its established boolean
  review and output contract and makes existing saved workflows harder to reason about.
- Chain Conditions: already possible, but cumbersome to author and review as cases grow.
- A separate Switch: recommended; existing Conditions keep their behavior and documents.

## Rules and execution

- Required input: `value`, with the same runtime value handling as Condition.
- Output: `branch`, the selected case identifier or `default`.
- Configure 1–15 ordered cases, plus one mandatory default route. This retains the
  existing limit of 16 control handles.
- Each case has a unique stable identifier, a display label and a validated Condition
  predicate. `default` and `error` are reserved; public identifiers follow the existing
  control-handle grammar.
- Evaluate cases in author order. The first true predicate wins; later predicates do
  not run. If none matches, select `default`.
- A comparison error fails execution with its reason. It never silently selects the
  default or continues to another case. Like Condition, Switch requires `on_error: fail`.
- Exactly one outgoing edge is required for each case and for default. Unknown,
  duplicate and missing route handles are validation errors.
- Editing labels or reordering cases preserves their identifiers and connections.
  Removing a connected case requires an explicit editor action to remove its edges.
- Case identifiers are generated by the editor and hidden from ordinary label editing.
  Export/import preserves them; labels never serve as identifiers or authorization.

Example: a verified `category` of `billing` selects the Billing case. An unfamiliar
category selects Other. A missing field required by an evaluated predicate is an error,
not proof that the Other case applies.

## Compiler and data availability

Replace the definition-only `control_routes(definition)` execution interface with one
node-aware route resolver. It resolves configured Switch handles and the existing static
handles of other nodes. Update every backend and frontend instance-route caller:
validation, platform-graph checks, compilation, fresh output, checkpoint restore and
editor rendering. No definition-only fallback may produce routes for a node instance.

Registry construction still needs to validate a node type before an instance and its
configuration exist. Keep this as metadata validation, not an alternative route resolver.
Registry validation checks the branch output and static/configurable route declaration;
instance handles come only from the node-aware resolver. Shared fixtures pin backend and
frontend results. A conformance test exercises every instance-route boundary with Switch,
including an undeclared branch injected into a saved checkpoint.

Only the selected path executes. Existing outcome-aware availability checks remain:
a later consumer cannot bind an output from a sibling case that may never have run.
Any traversal introduced here must remain bounded and cycle-aware.

## Verification and supported inputs

Switch uses the existing execution-policy boundary, but does not pause for its own human
review. It requires either an exact eligible verification binding or trusted non-model
source data, including deterministic derivations that preserve that trust. A manually
confirmed upstream verification remains valid under the existing rules.

"Trusted" is the existing rule, not a new list: `provenance.independent_source` (Chat
input, Manual trigger, and the Jira, Confluence and GitHub read operations), outputs of
Request reader and Verify extraction with a valid receipt, and Prompt or Calculate outputs
derived only from those. It is the same rule under which a Condition needs no review.

Raw model output is not acceptable merely because one field has a quoted provenance
label. Untrusted HTTP/Python results and other unsupported inputs are refused with a
node-specific error: "Route on checked values, or use a Condition, which supports review."

Reject unsupported lineage at validation where it is knowable. At execution and resume,
recheck the actual input, runtime-owned provenance, verification scope and any existing
upstream confirmation. A verifier's presence in the graph alone grants no permission.
Switch requires a contract-2 workflow, as the Request reader does. In contract 1,
validation refuses it ("Switch requires a contract-2 workflow"), so contract 1 needs no
second enforcement path. Existing Condition nodes keep their behavior.

Selecting a branch grants no new authority. A case named `approved` has exactly the same
write eligibility and approval requirements as any other case. It cannot relabel input,
authorize a changed payload, or bypass an upstream manual confirmation. No routing-review
metadata, database schema, approval endpoint or existing review screen changes in A5.2.

## Durability and observability

Checkpoint the selected route under the existing fenced success-event transaction.
Resume validates that it is a declared route, that it matches the current saved input and
ordered policy, and that input eligibility and any upstream confirmation still hold.
It neither repeats completed actions nor grants fresh budget.
Preserve uncertain-write refusal and durable action-result replay.

Use existing node events and accounting. Record the selected route; existing upstream
manual confirmations remain visible as their own events. Structured journal lines
contain identifiers and codes, not input or rule content.

## Editor

Provide a Switch palette entry and an ordered case editor using the existing typed
condition controls. Show named output handles and an always-visible Default handle.
Support adding, reordering and explicitly removing cases without stale bindings or
silently deleting connections. Invalid drafts remain saveable but cannot run.

Warn, without blocking, when a later case has an identical normalized predicate to an
earlier case and therefore cannot win. Bound this check to provable duplicates; no general
predicate-overlap solver is required. Existing true/false review screens stay unchanged.

## Acceptance

1. Exact numeric, text, membership and empty predicates match Condition semantics.
2. First match, overlapping cases, default, invalid comparisons and configuration errors
   each have direct regression tests. Zero and false remain real values.
3. Every configured route has exactly one edge; undeclared runtime/checkpoint routes
   are rejected through the node-aware resolver. One conformance test exercises validation,
   platform graph, compilation, fresh output and cached output. Unselected cases make no
   model or external tool calls. Remove stale definition-only instance-route calls.
4. Compiler and runtime tests reject unchecked-value bypasses, including attachments,
   recovery paths, forged provenance/receipts, and a Switch in a contract-1 workflow. A case named `approved` cannot bypass write eligibility or write approval.
5. Durable worker tests cover trusted sources, exact verified values, deterministic
   derivations, unsupported HTTP/Python/model values and changed/stale receipts on resume.
   Existing upstream human verification and write approvals retain expiry, digest, tenant
   and idempotency behavior. Switch creates no new review kind.
6. Process interruption around checkpoint and send preserves fencing and idempotency.
   Existing SQLite/PostgreSQL schema and conformance checks remain green; no migration is
   introduced by this phase.
7. Browser tests cover case editing, stable identifiers when labels/order change, explicit
   removal of connected cases, duplicate-predicate warnings and old-workflow compatibility.
8. A deployed support-routing scenario uses structured JSON input with explicit summary
   and category, matching the existing source-field verification rules. It observes exactly
   one receiver path. Separate fault cases observe no sends from unselected or unauthorized
   paths. Prose classification quality is not claimed by this scenario.
9. Run the backend/frontend regression checks and deployed campaign, then verify hosted
   CI on the exact pushed implementation commit. Evidence distinguishes test fixtures
   from live-model quality results.

## Delivery sequence after design approval

1. Backend: node-aware route contract, Switch predicates, compiler/runtime enforcement
   and checked/trusted-input restriction, with conformance and bypass tests.
2. Editor: ordered case controls, handles, connection stability, duplicate warnings and
   browser tests; existing review UI remains unchanged.
3. Structured-input deployed scenario, fault/recovery cases, final regression evidence
   and operator documentation.
