# Multi-way routing: the Switch node (A5.2)

A **Switch** reads one value and takes exactly one of several named paths. Example: a
checked support category goes to Billing, Technical, Account, or Default.

## Rules

1. **Cases.** 1–15 ordered cases, plus an automatic **Default** path. Each case is a full
   [typed condition](typed-conditions.md): operator, optional field, operands. Numbers,
   text, membership and empty values behave exactly as in a Condition.
2. **Order.** Cases are checked from the top. The first true case wins, and later cases are
   not evaluated. If no case matches, the run takes Default.
3. **Errors.** A comparison error (for example text where a number is needed, or a missing
   field in a case that is evaluated) fails the run with the reason. It never takes
   Default and never tries the next case. A Switch cannot use `on_error: continue` or
   `route`.
4. **Connections.** Each case and Default need exactly one outgoing connection. Unknown,
   duplicate and missing handles are validation errors.
5. **Case ids.** Each case has a route id (`case_` plus 6 characters), generated by the
   editor and kept when the case is renamed or moved, so its connection stays attached.
   `default` and `error` are reserved. A label is only text; it is never an id.

## Which values a Switch may route on

A Switch decides a business path, so it accepts only **checked or trusted** values, and only
in a **contract-2** workflow ("Switch requires a contract-2 workflow").

| Accepted | Refused |
| --- | --- |
| Values checked by the Request reader or Verify extraction | Raw model output (Agent, LLM, Query) |
| The trigger message | HTTP and Python tool results |
| Jira, Confluence and GitHub **read** results, whoever wrote their query | Write responses |
| Prompt or Calculate built only from the values above | A Calculate over an unchecked model extraction |

This is the existing trust rule (`provenance.independent_source` and verification
receipts), not a new list. Validation and execution apply it through one function
(`compiler.switch_input_allowed` and the same lineage walk at run time), so a workflow
that validates is not refused later for the same input. Refused inputs get: "Route on
checked values, or use a Condition, which supports review." A Switch never creates a
review of its own.

## What a route does not grant

A case id or label grants nothing. A case named `approved` is an ordinary path: a write
after it still needs a checked value and still waits for its own write approval.

## Durability

The chosen route is saved with the node's checkpoint. On resume it must be a declared
route, the input must still be eligible, and the route is recomputed from the input and
cases; a saved route that differs (for example, edited in the database) fails the run
before any send. Completed writes are not repeated.

## In the editor

- The case list edits labels and rules, adds cases, and moves or removes them. Removing a
  case with a connection removes both in one step (one Undo restores both).
- A case that cannot be edited safely (wrong shape, or a route id that is reserved,
  invalid or used twice) is shown with its saved data and repair buttons. Repair keeps the
  label and a well-shaped rule; a reserved route such as Default never moves.
- A later case with exactly the same rule as an earlier one gets a warning: it can never
  match. Rules that differ only in spacing are not flagged.
- On the canvas, each route has its own row with its handle on the right edge, so up to
  15 cases and Default stay readable. Lines start at the right edge; place targets to the
  right of the Switch for clean lines.

## Not in A5.2

- A person choosing a route by hand (a routing review). Use a Condition, which supports
  decision review, for values that cannot be checked.
- Parallel branches and joins (A5.3). Regular expressions. Automatic canvas layout.
